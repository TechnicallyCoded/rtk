• Based on the Skyblock shop fix workflow, the biggest RTK optimization is around broad rg output, not
  the later git/MR steps.

  ## RTK improvements specific to that task

  1. rg should detect huge single-line/generated matches

  Affected command class: rtk rg

  Evidence: My search for houe3x3x3|houe3x3_leg|houe across Configuration Plugins dumped a massive
  Plugins/HypingHelp/Plugin/classifier-model/tokenizer.json line. That was not useful for the shop-menu
  fix.

  General fix: If a matching line exceeds a threshold or looks like generated JSON/model/tokenizer/
  minified content, show:

  - file path
  - match count
  - first short snippet around the match
  - line length
  - guidance to use rg-verbose for full lines

  Why not one-off: Applies to all huge-line generated/minified files, not just tokenizer.json.

  Expected effect: High for accidental broad searches. It would have removed the single largest useless
  emitted chunk from that task.

  Risk: Low-medium. Sometimes the full long line matters, but rarely in initial discovery.

  Escape hatch: rtk rg-verbose ... or rtk rg --full-lines ....

  2. rg should summarize excessive broad search results

  Affected command class: rtk rg over large roots.

  Evidence: The first useful search returned many matches across Survival, Earth, Skyblock, crates,
  menus, items, pass files, plugin source, and generated assets. The actual fix was one Skyblock menu
  file.

  General fix: When results exceed a threshold, RTK should print:

  - total matches
  - matching file count
  - top files by match count
  - grouped roots, e.g. Configuration/Skyblock, Configuration/Earth, Plugins
  - first N representative lines
  - prompt to narrow by path or glob

  Why not one-off: Broad code/config searches are common.

  Expected effect: Medium-high. Less raw output while preserving enough signal to choose Configuration/
  Skyblock/plugins/HypingMenus.

  Risk: Medium. The hidden result might be the relevant one.

  Escape hatch: rtk rg-verbose ....

  3. find wrapper should explain unsupported predicates better

  Affected command class: rtk find

  Evidence: My first find command failed because RTK does not support compound predicates/actions. It
  returned a clear error, but did not suggest a supported equivalent.

  General fix: When rejecting compound predicates, print examples:

  - “Use direct find for compound predicates”
  - “Or split into multiple simple rtk find calls”
  - “Or use rtk rg --files -g ... for filename filtering”

  Why not one-off: Applies to all unsupported find expressions.

  Expected effect: Low token savings, medium workflow efficiency. It prevents retries and broad
  fallback searches.

  Risk: Very low.

  Escape hatch: Direct find, as already suggested.

  4. RTK should support project/root-aware search narrowing hints

  Affected command class: rtk rg, rtk find

  Evidence: The user said “shop menus (skyblock)”, but my broad search included Plugins, Survival, and
  Earth. RTK cannot know intent, but it can detect that one root dominates useful-looking matches.

  General fix: For broad searches over sibling roots, summarize by root and suggest narrower reruns:

  - Configuration/Skyblock
  - Configuration/Skyblock/plugins/HypingMenus
  - Configuration/Skyblock/plugins/NewHypingItems

  Why not one-off: Applies to monorepos and multi-server config repos generally.

  Expected effect: Medium. It would reduce exploration output and make the next command obvious.

  Risk: Low. It suggests narrowing rather than hiding by default.

  Escape hatch: Continue using broad rg-verbose.

  5. git status/git remote could be compacted into a config-repo preflight summary

  Affected command class: rtk git status, rtk git remote -v

  Evidence: For the MR workflow I ran separate status and remote checks. Output was small, so token
  impact is not huge, but this happens frequently in config work.

  General fix: Add a command like rtk git preflight or compact existing output when both are requested
  near each other:

  - current branch
  - dirty files count/list
  - remotes names and push URLs summarized
  - whether origin/preprod exists

  Why not one-off: Applies to all repo preflight checks.

  Expected effect: Low token savings, moderate workflow simplification.

  Risk: Low.

  Escape hatch: rtk git status --verbose, rtk git remote -v.

  ## User command habits from that task

  1. I should have searched Configuration/Skyblock first, not Configuration Plugins.
  2. I should have included plugins/HypingMenus earlier because the user specifically said “shop
     menus”.
  3. I should avoid broad patterns like houe unless the first targeted IDs fail.
  4. For config fixes requiring MR, start directly from the proper config repo/worktree path before
     reading current branch files, to avoid reading stale/different branch content.
  5. Use rg --glob exclusions for obvious generated/model files if doing broad repo searches, e.g.
     exclude tokenizer/model artifacts.

  Implement rg huge-line suppression plus broad-result summaries first.

  That would have improved the workflow most because the main waste came from one broad search emitting
  irrelevant generated content and too many cross-server matches.
